# 设计文档阶段工程化约束原则

## 🔥 TL;DR - 立即开始
> **目标**：内容创作者掌握设计文档阶段的严格工程化约束标准
> 
> **行动**：1. 理解[贯通流程定位](#🔄-贯通流程中的设计定位) → 2. 确保[输入依赖](#📥-输入依赖原则) → 3. 执行[研究要求](#🔍-研究要求原则) → 4. 应用[结构标准](#🏗️-结构标准原则)
> 
> **核心价值**：设计阶段是贯通流程的技术转化器，基于需求输入进行架构设计，为实施规划TDD做充分准备

## 🔄 贯通流程中的设计定位

### 贯通流程理念在设计阶段的体现
**核心认知转变**：设计文档不是独立技术文档，而是贯通流程中的技术转化环节

```
贯通流程中的设计(Design)定位：
需求(Requirements)规格 → [设计(Design)文档专业分工] → 技术架构方案 → [实施规划(Implementation)输入]
           ↑                       ↓
       业务理解输入         技术方案输出
       验收标准输入         测试策略输出
           ↓                       ↓
       严格技术研究         为TDD做充分准备
       架构决策记录         可测试性设计
```

### 严格依赖关系的价值
- **需求忠实转化**：将业务需求忠实转化为技术方案，避免理解偏差
- **确保质量递进**：通过质量门禁确保技术方案质量再进入实施规划(Implementation)
- **支持TDD准备**：为实施规划(Implementation)阶段（TDD真正主场）做充分技术准备
- **建立架构思维**：从需求开始就考虑如何支持最终测试计划的精确执行

### 与前后阶段的输入输出对接
```
设计(Design)文档阶段在贯通流程中的职责：
输入：**需求(Requirements)规格交付物** (`requirements/` 或等效载体)，来自需求(Requirements)阶段的严格依赖。
处理：技术研究、架构设计、可测试性设计。
输出：**设计(Design)规格交付物** (`design/` 或等效载体)，该交付物将成为实施规划(Implementation)阶段的唯一输入依据。
质量门禁：技术方案可行性验证，确保输出质量。
```

### 🧪 TDD在设计阶段的正确定位
**核心原则**：可测试性设计，为TDD做准备（但不实施TDD）

```
TDD在设计阶段的职责边界：
✅ 应该做：可测试架构设计
✅ 应该做：测试策略规划（但不实施）
✅ 应该做：为TDD主场（实施规划）提供技术基础
❌ 不应做：编写具体测试用例
❌ 不应做：进行测试驱动开发
❌ 不应做：实施TDD的红绿重构循环
```

**价值体现**：为实施规划(Implementation)阶段（TDD真正主场）提供完整的技术架构基础

## 📥 输入依赖原则

### 🔒 严格输入要求
- **必须基于需求文档**：设计文档必须严格基于已批准的requirements/交付物（或requirements.md）
- **需求优先存在**：确保需求文档首先存在且获得批准
- **完整性检查**：验证需求文档包含所有必要的用户故事和验收标准

### ❌ 禁止行为
- **无需求设计**：绝不允许在没有需求文档的情况下开始设计
- **假设需求**：不能基于假设或口头描述进行设计
- **跳过验证**：不能跳过需求文档的完整性检查

### ✅ 正确做法
- **需求追溯**：设计中的每个决策都能追溯到具体需求
- **覆盖验证**：确保设计满足所有已确定的功能需求
- **版本同步**：基于最新批准版本的需求文档

### 🔗 严格依赖关系维护
**贯通流程核心机制**：设计阶段的每项决策都必须能追溯到需求依据

```
依赖关系检查清单：
□ 设计决策是否能追溯到具体需求条目？
□ 架构设计是否满足所有验收标准要求？
□ 技术选型是否符合需求中的技术约束？
□ 边缘情况处理是否覆盖需求中识别的场景？
□ 设计范围是否与需求范围一致？
```

**创作要求**：任何设计阶段内容都必须明确标注其需求来源，确保输入依赖的透明性和追溯性

## 🔍 研究要求原则

### 📋 强制研究流程
```
设计前必须完成的研究步骤：
1. 根据功能需求确定需要研究的技术领域
2. 进行必要的技术调研和方案对比
3. 在对话线程中建立研究上下文
4. 总结将为设计提供信息的关键发现
5. 引用来源并包含相关链接
```

### 🎯 研究领域识别
- **技术栈选择**：基于需求特点确定合适的技术栈
- **架构模式**：研究适用的架构模式和设计模式
- **性能要求**：调研性能基准和优化策略
- **安全考虑**：研究相关的安全最佳实践
- **第三方集成**：调研需要集成的外部服务和API

### 📊 研究质量标准
- **来源可信**：使用权威技术文档、官方指南、知名技术博客
- **信息时效**：确保研究信息是最新的、相关的
- **对比分析**：提供多种方案的优劣对比
- **决策依据**：明确说明选择特定技术方案的理由

### 🔄 贯通流程导向的研究方法
**设计理念**：研究不仅为当前设计服务，更要为后续实施规划提供充分基础

```
研究如何服务贯通流程：
技术调研结果 → 为架构设计提供选型依据
性能基准分析 → 为实施规划提供优化策略
安全最佳实践 → 为任务执行提供安全指导
第三方集成调研 → 为测试策略提供依赖考虑
```

**创作要求**：研究过程必须透明，关键发现必须记录，为设计决策提供充分依据，同时服务后续阶段

## 🏗️ 结构标准原则

### 📋 固定文档结构
```markdown
# 功能设计文档

## 1. 概述
[基于需求的功能概述，说明设计目标和范围]

## 2. 架构
[整体架构设计，包含组件关系和数据流]

## 3. 组件和接口
[各组件的详细设计和接口定义]

## 4. 数据模型
[数据结构设计和存储策略]

## 5. 错误处理
[异常情况处理策略和错误恢复机制]

## 6. 测试策略
[针对设计的测试方法和验证策略]

## 7. 设计决策记录
[重要设计决策及其理由说明]
```

### 🎯 各部分详细要求

#### 📊 架构部分要求
- **组件图**：使用Mermaid绘制架构图（如适用）
- **数据流**：清晰描述数据在系统中的流转路径
- **边界定义**：明确系统边界和外部依赖

#### 🔗 接口部分要求
- **接口规范**：详细定义输入输出格式
- **通信协议**：说明组件间的通信方式
- **版本策略**：考虑接口的版本管理

#### 🗄️ 数据模型要求
- **实体关系**：定义核心实体及其关系
- **约束规则**：说明数据完整性约束
- **存储策略**：选择合适的存储方案

### 🔄 贯通流程导向的结构设计
**设计理念**：结构不仅是文档组织工具，更是贯通流程的知识传递机制

```
结构如何服务贯通流程：
概述部分 → 为实施规划提供项目理解基础
架构部分 → 为任务分解提供系统边界和依赖
接口部分 → 为测试用例设计提供精确标准
数据模型 → 为测试数据准备提供结构指导
错误处理 → 为异常测试提供场景指导
测试策略 → 为TDD主场提供最直接的转化基础
```

**创作要求**：严格按照固定结构组织内容，确保设计文档的完整性和与后续阶段的对接性

## 🔒 质量门禁原则

### 📋 审批流程要求
```
设计文档完成后的强制流程：
1. 创建design/目录结构，包含所有必需部分的专项文档
2. 将研究结果直接纳入设计过程
3. 必须询问："设计看起来可以吗？如果可以，我们可以继续制定实施计划。"
4. 等待明确批准（"是"、"已批准"、"看起来不错"等）
5. 如未获批准，必须修改设计文档
6. 继续反馈-修订循环，直到获得明确批准
```

### 🎯 设计质量检查（机器可执行清单）

#### 📝 内容完整性检查
- [ ] **需求覆盖检查**：设计方案覆盖requirements/交付物中所有功能需求，每个需求都有对应设计决策
- [ ] **研究基础检查**：设计决策均基于充分的技术调研，包含外部来源和对比分析
- [ ] **固定结构检查**：包含概述、架构、组件和接口、数据模型、错误处理、测试策略六个部分
- [ ] **决策记录检查**：重要技术决策都有明确的理由说明和需求追溯

#### 🖼️ 视觉化和可测试性检查
- [ ] **架构图表检查**：包含Mermaid绘制的架构图或系统边界图，清晰展示组件关系
- [ ] **接口设计检查**：每个组件的输入输出接口都有明确定义，为测试用例设计做准备
- [ ] **可测试性设计检查**：为实施规划(Implementation)阶段TDD转换提供充分技术准备
- [ ] **错误处理检查**：覆盖需求中识别的所有边缘情况，为异常测试提供场景指导

#### 🔗 贯通流程对接检查
- [ ] **输出格式检查**：生成design/目录结构（实战模式）或design.md（教学模式），符合实施规划(Implementation)阶段输入要求
- [ ] **批准流程检查**：使用标准话术“设计看起来可以吗？如果可以，我们可以继续制定实施计划。”
- [ ] **明确批准获得**：收到用户的“是”、“已批准”、“看起来不错”等明确正面回应

### 🔄 反馈处理机制
- **差距识别**：如发现需求理解差距，必须提议返回需求澄清
- **用户反馈整合**：必须将所有用户反馈纳入设计文档
- **技术决策征询**：可就具体技术决策征求用户意见

### 🔄 贯通流程质量递进机制
**核心价值**：质量门禁不仅保证设计质量，更确保实施规划阶段的顺利转化

```
质量门禁在贯通流程中的作用：
设计方案可行性验证 → 避免不切实际的技术方案进入规划
技术决策完整性确认 → 确保实施规划有充分依据
可测试性设计验证 → 确保能支持TDD主场的测试转化
架构决策追溯性 → 确保每项决策都有明确的需求依据
```

**创作要求**：设计阶段的质量门禁确保技术方案的可行性和与贯通流程的对接完整性

### 🤖 AI协作执行指导

**基于实战提示词的具体执行约束**：

#### 📁 文件操作和结构约束
- **文件操作**: AI必须根据**输出目标与格式原则**创建对应的`design/`目录结构（实战模式优先）或等效载体，并确保其包含所有必需部分。
- **标准结构强制**：必须包含以下固定部分：
  - 概述（基于需求的功能概述）
  - 架构（整体架构设计，包含组件关系和数据流）
  - 组件和接口（各组件的详细设计和接口定义）
  - 数据模型（数据结构设计和存储策略）
  - 错误处理（异常情况处理策略和错误恢复机制）
  - 测试策略（针对设计的测试方法和验证策略）
- **可视化要求**：适当时包含图表或视觉表示，优先使用Mermaid绘制图表

#### 🔍 研究驱动设计流程
- **领域识别**：必须根据功能需求确定需要研究的技术领域
- **上下文建立**：必须进行研究并在对话线程中建立上下文
- **来源引用**：应在对话中引用来源并包含相关链接
- **关键发现总结**：必须总结将为功能设计提供信息的关键发现
- **禁止分离**：不应创建单独的研究文件，而应将研究用作设计的上下文
- **直接纳入**：必须将研究结果直接纳入设计过程

#### 🎯 需求依赖严格验证
- **基础验证**：设计文档必须基于需求文档，确保需求文档首先存在
- **覆盖性检查**：必须确保设计满足需求澄清过程中确定的所有功能需求
- **追溯性保证**：每个设计决策都能追溯到具体需求条目
- **决策记录**：必须突出显示设计决策及其理由

#### 💬 交互标准化协议
- **标准询问话术**：必须使用固定话术"设计看起来可以吗？如果可以，我们可以继续制定实施计划。"
- **批准标准明确**：只接受"是"、"已批准"、"看起来不错"等明确正面回应
- **修改请求处理**：如用户请求更改或未明确批准，必须对设计文档进行修改
- **反馈整合**：必须将所有用户反馈纳入设计文档
- **征询机制**：可就具体技术决策征求用户意见

#### 🔄 上溯和差距处理机制
- **差距识别**：如在设计过程中发现需求理解差距，必须提议返回需求澄清
- **完整性检查**：如发现需求不完整，必须返回需求澄清步骤
- **技术可行性**：如发现技术方案不可行，必须重新评估或返回需求
- **依赖验证**：确保所有设计决策都有明确的需求依据

#### 🔄 贯通流程导向的AI协作
**核心理念**：AI协作必须体现设计阶段在贯通流程中的技术转化作用

```
AI协作如何服务贯通流程：
研究驱动策略 → 确保技术方案基于充分调研和分析
需求忠实转化 → 保证设计方案忠实反映业务需求
架构决策记录 → 为实施规划提供完整的技术基础  
可测试性设计 → 为TDD主场提供充分的技术准备
```

**AI执行要求**：严格遵循研究-设计-验证的标准流程，确保设计阶段的技术转化质量和贯通流程对接完整性

## 📤 输出目标与格式原则

本阶段的输出必须能无缝成为下一阶段的输入。

#### 📤 输出目标与格式
- **交付物**: `design/` 或等效载体
- **结构示例** (泛化模式):
    ```
    design/
    ├── README.md                    # 设计文档结构总览和阅读指南
    ├── [架构设计文档]               # 示例: architecture.md, system_design.md, components.md
    ├── [数据设计文档]               # 示例: data_model.md, database_design.md, entities.md
    ├── [接口设计文档]               # 示例: api_spec.md, interfaces.md, protocols.md
    ├── [安全设计文档]               # 示例: security.md, auth_design.md, permissions.md
    └── [专项技术文档]               # 根据项目类型: ml_pipeline.md, blockchain_arch.md等
    ```
    
    **设计策略选择矩阵**:
    ```
    技术架构        项目阶段        设计文档重点              核心文档示例
    ────────────────────────────────────────────────────────────────────────────────────
    微服务架构      产品级         服务边界 + 数据一致性        service_boundaries.md, data_consistency.md
    单体应用        MVP/原型       核心流程 + 数据结构          core_flows.md, data_models.md
    事件驱动架构    复杂业务       事件设计 + 状态管理          event_catalog.md, state_machines.md
    无服务架构      云原生         函数设计 + 资源管理          function_specs.md, resource_topology.md
    AI/ML系统       数据驱动       模型架构 + 数据管道          model_architecture.md, data_pipelines.md
    区块链系统      去中心化       合约设计 + 共识机制          smart_contracts.md, consensus_design.md
    IoT平台         边缘计算       设备管理 + 通信协议          device_management.md, protocols.md
    ```
    
    **技术决策树**:
    1. **评估性能需求** → 选择架构模式(单体 vs 分布式)
    2. **分析数据复杂度** → 设计存储策略(关系型 vs NoSQL vs 混合)
    3. **考量安全级别** → 制定安全架构(零信任 vs 传统边界)
    4. **确定集成策略** → 设计接口规范(REST vs GraphQL vs gRPC)
- **AI设计决策引擎**:
  ```
  // 架构复杂度评估
  IF requirements.complexity == "high" AND team.experience == "senior" THEN
      architecture_style = "microservices" OR "event_driven"
      documentation_depth = "detailed_with_diagrams"
      focus_areas = ["service_boundaries", "data_consistency", "failure_handling"]
      
  // 数据密集型项目
  ELIF requirements.data_volume == "large" OR requirements.analytics == true THEN
      architecture_style = "data_mesh" OR "lambda_architecture"
      documentation_depth = "pipeline_focused"
      focus_areas = ["data_lineage", "quality_gates", "privacy_compliance"]
      
  // 快速原型项目  
  ELIF project.timeline <= "4_weeks" AND project.stage == "prototype" THEN
      architecture_style = "monolithic" OR "jamstack"
      documentation_depth = "core_components_only"
      focus_areas = ["key_workflows", "data_models", "api_contracts"]
  ```
  
  **设计防错指南**:
  - ✘️ 勿在早期原型中过度设计微服务架构
  - ✘️ 勿在数据敏感项目中忽略隐私设计
  - ✘️ 勿在高并发场景下选择单线程架构
  - ✓️ 始终保证设计能支撑需求中的所有验收标准

### 🔗 严格依赖关系维护
**贯通流程核心机制**: 无论交付物是文件还是目录，其整体都将作为下一阶段（实施规划）的严格输入。
```
依赖关系检查清单：
□ 设计交付物（文件或目录）是否能直接指导实施规划阶段的任务分解？
□ 接口设计是否能直接转化为测试用例？
□ 数据模型是否能支持测试数据准备？
□ 错误处理是否能转化为异常测试场景？
□ 测试策略是否能直接指导TDD实施？
```
**创作要求**：确保设计阶段输出能无缝成为实施规划阶段输入，体现贯通流程的严格依赖关系。

## 🎯 可测试性设计要求

### 🧪 测试策略规划
- **单元测试**：为每个组件设计单元测试策略
- **集成测试**：规划组件间接口的集成测试
- **端到端测试**：设计用户场景的完整测试流程

### 📊 验证点设计
- **功能验证**：每个功能模块的验证方法
- **性能验证**：关键性能指标的测试方法
- **安全验证**：安全特性的验证策略

### 🔄 TDD准备
- **测试优先思维**：为TDD实施做好设计准备
- **测试接口**：设计便于测试的组件接口
- **模拟策略**：规划测试中的依赖模拟方案

### 🔄 为TDD主场做凅备的核心价值
**贯通流程意义**：设计阶段的可测试性设计直接决定实施规划阶段TDD转化的成功率

```
TDD准备在贯通流程中的作用：
可测试架构 → 为红绿重构循环提供稳固架构基础
测试策略规划 → 为测试用例设计提供系统性指导
测试接口设计 → 为后续AI精确执行提供可操作接口
模拟策略规划 → 为外部依赖测试提供隔离方案
```

**创作要求**：设计阶段为TDD主场（实施规划）做好充分准备，但不越界实施TDD，保持专业分工

## 🚨 常见违反原则的行为

### ❌ 输入依赖违反
- 在没有需求文档的情况下开始设计
- 基于口头描述而非正式需求文档
- 忽略需求中的关键约束条件

### ❌ 研究要求违反
- 跳过技术调研直接选择方案
- 使用过时或不可信的技术信息
- 未记录设计决策的依据

### ❌ 结构标准违反
- 缺少必需的文档部分
- 架构图不清晰或缺失
- 未考虑错误处理和测试策略

**修正策略**：发现违反后立即补充缺失部分，重新执行正确的设计流程

## 🎯 应用此原则

### 📝 内容创作者使用方法
1. **设计前准备**：确保需求文档完整，制定研究计划
2. **设计中执行**：严格按照结构标准组织内容，记录设计决策
3. **设计后验证**：使用质量检查清单全面检查
4. **交付时把关**：严格执行质量门禁流程

### 🔧 质量保证要求
- 定期review设计文档是否符合结构标准
- 验证研究质量和设计决策的合理性
- 确保可测试性设计要求得到满足

### 📊 质量标准维度
1. **贯通流程体现度**：是否清楚体现与前后阶段的严格依赖关系
2. **专业分工清晰度**：是否明确定义设计阶段应做和不应做的内容
3. **TDD定位准确度**：是否正确定位TDD在设计阶段的作用边界
4. **输入输出对接完整度**：是否确保与前后阶段的无缝衔接
5. **用户友好度**：是否避免专业术语，使用通俗易懂表达
