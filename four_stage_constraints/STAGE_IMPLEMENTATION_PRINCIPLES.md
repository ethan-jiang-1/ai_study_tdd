## 🔄 贯通流程中的实施规划定位

### 贯通流程理念在实施规划阶段的体现
**核心认知转变**：实施规划不是独立的任务分解，而是贯通流程中的关键转折点和TDD主场

```
贯通流程中的实施规划(Implementation)定位：
设计(Design)方案 → [实施规划(Implementation)专业分工] → 完备测试计划 → [任务规划(Tasks)输入]
        ↑                   ↓
    技术架构输入         测试驱动任务输出
    可测试性设计         TDD执行指导
        ↓                   ↓
    关键转折点：从技术设计转换到测试驱动实施
    TDD真正主场：将设计转换为可执行的测试计划
```

### 严格依赖关系的价值
- **设计到测试的转换**：将技术架构忠实转换为测试驱动的执行计划
- **确保质量递进**：通过质量门禁确保测试计划完备性再进入执行
- **支持TDD代码生产**：产出的测试计划能指导后续AI进行精确的TDD实施
- **建立执行思维**：从设计开始就为后续的精确执行建立完整路径

### 与前后阶段的输入输出对接
```
实施规划(Implementation)阶段在贯通流程中的职责：
输入：**设计(Design)规格交付物** (`design/` 或等效载体)，来自设计(Design)阶段的严格依赖。
处理：TDD转换、任务分解、测试计划制定。
输出：**实施规划(Implementation)交付物** (`implementation/` 或等效载体)，该交付物将成为任务规划(Tasks)阶段的唯一输入依据。
质量门禁：测试计划完备性验证，确保输出质量。
```

### 🧪 TDD在实施规划阶段的主场地位
**核心原则**：⭐ TDD的真正主场 - 将需求+设计转换为测试驱动编码任务

```
TDD在实施规划阶段的核心职责：
✅ 应该做：将功能设计转换为测试驱动的编码任务序列
✅ 应该做：制定完备的测试计划，支持红绿重构循环
✅ 应该做：为任务规划(Tasks)阶段提供精确的TDD实施指导
✅ 应该做：确保每个任务都有明确的测试验证方法
❌ 不应做：实际执行TDD（属于任务规划(Tasks)阶段职责）
❌ 不应做：编写具体代码（专注于计划制定）
```

**价值体现**：为任务规划(Tasks)阶段（TDD执行任务规划文档化）提供完整的测试驱动指导方案

## ⭐ TDD转换职责原则

### 🎯 核心职责定义
**实施规划是TDD转换的真正主场**：将功能设计转换为测试驱动的编码任务

### 📋 TDD转换具体要求
```
核心转换任务：
"将功能设计转换为implementation/目录结构，为后续TDD代码生产阶段提供测试驱动的任务指导。
优先考虑最佳实践、增量进度和早期测试，确保在任何阶段都不会出现大的复杂性跳跃。"
```

### 🧪 测试驱动思维要求
- **测试优先设计**：每个任务都要考虑如何测试
- **红绿重构循环**：任务序列要支持TDD循环
- **早期测试验证**：安排步骤以便后续代码实施能尽早验证核心功能
- **可测试任务分解**：确保每个任务都能被独立测试

### ✅ 转换质量标准
- [ ] 每个任务都包含测试驱动的执行方式
- [ ] 任务序列支持增量验证
- [ ] 复杂功能被分解为可测试的小步骤
- [ ] 测试用例能直接指导后续代码生产

### 🔄 贯通流程导向的TDD转换价值
**设计理念**：TDD转换不仅服务当前规划，更要确保任务规划(Tasks)阶段的精确文档化

```
TDD转换如何服务贯通流程：
功能设计理解 → 为测试用例设计提供业务逻辑基础
架构方案转换 → 为TDD实施提供技术框架指导
测试策略实施 → 为后续AI精确执行提供详细测试计划
增量构建设计 → 为红绿重构循环提供步骤化指导
```

**创作要求**：实施规划必须体现TDD主场定位，确保转换结果能无缝支持任务规划(Tasks)阶段的严格TDD实施

## 📋 任务格式标准原则

### 🔒 强制格式要求
```markdown
# 实施任务清单

## 任务列表

### 1. [功能模块名称]
- [ ] 1.1 [具体编码任务] 
  - 任务目标：[明确的编码目标]
  - 需求引用：参考requirements/交付物第X条
  - 测试要求：[具体的测试验证方法]
  - 预期输出：[该任务的交付物]

- [ ] 1.2 [具体编码任务]
  - 任务目标：[明确的编码目标]
  - 需求引用：参考requirements/交付物第X条
  - 测试要求：[具体的测试验证方法] 
  - 预期输出：[该任务的交付物]

### 2. [功能模块名称]
[重复相同格式]
```

### 📊 格式约束细则
- **最多两级层次结构**：顶层项目（如史诗）仅在需要时使用
- **十进制编号**：子任务使用十进制表示法（1.1、1.2、2.1）
- **复选框强制**：每个项目都必须是一个复选框
- **偏好简单结构**：避免过度复杂的嵌套

### 🎯 任务描述要求
- **明确目标**：任务描述必须是具体的编码目标
- **代码导向**：涉及编写、修改或测试特定的代码组件
- **可操作性**：编码代理无需额外澄清即可执行
- **需求追溯**：每个任务都引用需求文档中的具体需求

### 🔄 贯通流程导向的格式设计
**设计理念**：格式不仅是任务组织工具，更是贯通流程的精确传递机制

```
格式如何服务贯通流程：
任务目标描述 → 为AI执行提供明确的编码指导
需求引用机制 → 确保任务与原始需求的可追溯性
测试要求规格 → 为TDD循环提供精确的验证标准
预期输出定义 → 为质量验证提供明确的交付标准
```

**创作要求**：严格遵循格式标准，确保任务列表能无缝指导任务规划(Tasks)阶段的AI协作文档化

## 🔄 增量构建原则

### 📈 增量进度要求
- **步骤依赖**：每个步骤都以增量方式建立在先前步骤的基础上
- **连接性**：确保每个提示都建立在先前提示的基础上
- **无悬空代码**：不应有未集成到上一步中的悬空或孤立代码
- **集成收尾**：以将所有内容连接在一起结束

### 🧩 复杂性控制
- **避免大跳跃**：确保在任何阶段都不会出现大的复杂性跳跃
- **渐进式实现**：复杂功能分解为多个简单步骤
- **验证节点**：关键节点设置验证和测试

### 🔗 任务连贯性
```
正确的任务序列示例：
1.1 创建基础数据模型 → 为1.2提供数据结构基础
1.2 实现基础CRUD操作 → 基于1.1的数据模型
1.3 添加业务逻辑验证 → 基于1.2的基础操作
1.4 集成测试验证 → 验证1.1-1.3的集成效果
```

### 🔄 贯通流程导向的增量构建价值
**设计理念**：增量构建不仅保证开发安全，更体现贯通流程的系统性思维

```
增量构建如何服务贯通流程：
步骤依赖设计 → 为任务执行提供安全的推进路径
复杂性控制 → 为AI执行提供可管理的实施颗粒度
验证节点设置 → 为质量递进提供关键检查点
集成收尾机制 → 确保最终文档的系统完整性
```

**创作要求**：确保任务序列的逻辑连贯性，体现贯通流程的系统性和完整性，支持后续AI精确的增量执行

## 🔒 代码导向约束原则

### ✅ 必须包含的任务类型
- **编写代码**：实现特定功能的代码组件
- **修改代码**：基于需求变更修改现有代码
- **测试代码**：编写单元测试、集成测试等
- **调试代码**：修复bug和性能问题

### ❌ 严禁包含的任务类型
- **用户验收测试**：需要用户参与的测试活动
- **部署到生产**：部署和运维相关任务
- **性能指标收集**：监控和数据收集任务
- **用户培训**：培训和文档编写任务
- **业务流程变更**：组织和流程变更任务
- **营销沟通活动**：市场推广相关任务

### 🎯 可操作性检查标准
- [ ] 任务涉及编写、修改或测试特定的代码组件
- [ ] 任务指定需要创建或修改哪些文件或组件
- [ ] 任务足够具体，编码代理无需额外澄清即可执行
- [ ] 任务专注于实施细节而不是高级概念
- [ ] 任务限定于特定的编码活动

### 🔄 贯通流程导向的代码约束价值
**设计理念**：代码导向约束确保实施规划专注核心职责，服务贯通流程的精确执行

```
代码导向约束如何服务贯通流程：
编码任务专注 → 确保输出能指导后续TDD代码生产
可操作性保证 → 避免任务规划(Tasks)阶段的理解偏差
职责边界维护 → 保持实施规划与其他阶段的专业分工
执行效率优化 → 为后续AI精确执行提供最优化的任务颗粒度
```

**创作要求**：严格筛选任务类型，确保所有任务都能无缝指导任务规划(Tasks)阶段的AI协作文档化，体现贯通流程的专业分工原则

## 🔒 质量门禁原则

### 📋 审批流程要求
```
实施计划完成后的强制流程：
1. 创建implementation/目录结构，包含完整的测试驱动任务体系
2. 验证所有任务都可由编码代理执行
3. 确保任务覆盖设计的所有方面
4. 必须询问："任务看起来可以吗？"
5. 等待明确批准（"是"、"已批准"、"看起来不错"等）
6. 如未获批准，必须修改任务文档
7. 继续反馈-修订循环，直到获得明确批准
```

### 🎯 规划质量检查（机器可执行清单）

#### 📝 TDD转换质量检查
- [ ] **任务分解检查**：每个任务都是可独立执行的编码步骤，包含明确的编码目标
- [ ] **需求追溯检查**：每个任务都引用requirements/交付物中的具体需求条目，建立可追溯性
- [ ] **设计覆盖检查**：任务计划覆盖design/交付物中所有可编码实现的设计方面
- [ ] **测试驱动检查**：每个任务包含具体的测试要求和验证方法，支持红绿重构循环

#### 🔗 任务连贯性检查
- [ ] **增量构建检查**：任务序列体现逐步构建，每个任务都基于前一任务的成果
- [ ] **复杂性控制检查**：避免大的复杂性跳跃，复杂功能分解为多个简单步骤
- [ ] **集成收尾检查**：任务序列以将所有内容连接在一起结束，无悬空代码

#### 🚫 代码导向约束检查
- [ ] **编码任务检查**：所有任务都涉及编写、修改或测试具体的代码组件
- [ ] **非编码任务禁止检查**：不包含用户验收测试、部署、培训、营销等非编码任务
- [ ] **可操作性检查**：每个任务都足够具体，编码代理无需额外澄清即可执行

#### 🔗 贯通流程对接检查
- [ ] **输出格式检查**：生成implementation/目录结构（实战模式）或implementation.md（教学模式），符合任务规划(Tasks)阶段输入要求
- [ ] **批准流程检查**：使用标准话术“任务看起来可以吗？”并等待明确批准
- [ ] **明确批准获得**：收到用户的“是”、“已批准”、“看起来不错”等明确正面回应

### 🔄 差距处理机制
- **需求差距**：如发现需求理解差距，必须提议返回需求步骤
- **设计差距**：如发现设计不完整，必须提议返回设计步骤
- **实施差距**：在规划期间发现的技术难点必须解决

### 🔄 贯通流程质量递进机制
**核心价值**：质量门禁不仅保证规划质量，更确保任务规划(Tasks)阶段的顺利实施

```
质量门禁在贯通流程中的作用：
测试计划完备性验证 → 避免不完整的测试指导进入执行
任务可执行性确认 → 确保后续AI能精确理解和执行每个任务
依赖关系完整性检查 → 保证任务序列的逻辑连贯性
贯通流程一致性维护 → 确保与前阶段输出的严格对接
```

**创作要求**：实施规划的质量门禁确保测试计划的完备性和与贯通流程的完整对接

## 📤 输出目标与格式原则

本阶段的输出必须能无缝成为下一阶段的输入。

#### 📤 输出目标与格式
- **交付物**: `implementation/` 或等效载体
- **结构示例** (泛化模式):
    ```
    implementation/
    ├── README.md                   # 实施规划结构总览和阅读指南
    ├── [TDD策略文档]              # 示例: tdd_strategy.md, test_approach.md, qa_plan.md
    ├── [核心模块任务文档]         # 示例: backend_tasks.md, core_logic.md, data_layer.md
    ├── [用户界面任务文档]         # 示例: frontend_tasks.md, ui_components.md, user_flows.md
    ├── [集成计划文档]             # 示例: integration_plan.md, deployment.md, e2e_tests.md
    └── [专项技术任务]             # 根据项目类型: ml_training.md, smart_contracts.md等
    ```
    
    **TDD实施策略矩阵**:
    ```
    项目类型        测试复杂度      TDD方法论                  任务组织策略
    ────────────────────────────────────────────────────────────────────────────────────────────────
    API服务         中等            契约测试 + 集成测试        按端点分组 → endpoint_auth.md, endpoint_data.md
    复杂业务系统    高              BDD + 属性测试            按业务域分组 → domain_user.md, domain_order.md
    数据密集型      特殊            数据质量测试 + 性能测试    按数据流分组 → ingestion_tasks.md, processing_tasks.md
    前端应用        中低            组件测试 + E2E测试        按用户流分组 → user_journey_auth.md, user_journey_purchase.md
    AI/ML系统       特殊            模型验证 + A/B测试        按模型阶段分组 → model_training.md, model_serving.md
    实时系统        高              混沌测试 + 性能测试        按稳定性分组 → critical_path.md, degradation_scenarios.md
    ```
    
    **增量构建策略**:
    1. **风险评估优先** → 高风险模块优先实现和测试
    2. **依赖关系排序** → 基础组件 → 业务逻辑 → 用户界面 → 集成测试
    3. **早期验证设置** → 每个阶段都要有可演示的成果
    4. **反馈循环建立** → 保证每个任务都有快速验证机制
- **AI实施策略引擎**:
  ```
  // 任务分解精度决策
  IF design.complexity == "high" AND team.size > 8 THEN
      task_granularity = "fine_grained"  // 2-4小时/任务
      parallel_streams = design.modules.count
      verification_frequency = "per_task"
      
  // TDD方法选择
  ELIF requirements.user_stories.count > 20 AND business.complexity == "high" THEN
      tdd_approach = "BDD_driven"  // 从用户故事开始
      task_organization = "by_user_journey"
      acceptance_criteria = "gherkin_format"
      
  // 快速迭代模式
  ELIF project.timeline <= "6_weeks" AND team.experience == "senior" THEN
      tdd_approach = "outside_in"  // 从接口开始
      task_organization = "by_api_endpoint"
      verification_frequency = "per_feature"
  ```
  
  **实施防错检查点**:
  - ✘️ 勿在小团队中过度细分任务(小于2小时的任务)
  - ✘️ 勿在复杂业务中略过BDD的业务语言转换
  - ✘️ 勿在高并发场景下忽略线程安全测试
  - ✓️ 确保每个任务都有明确的“完成定义”(Definition of Done)

### 🔗 严格依赖关系维护
**贯通流程核心机制**: 无论交付物是文件还是目录，其整体都将作为下一阶段（任务执行）的严格输入。
```
依赖关系检查清单：
□ 实施规划交付物（文件或目录）是否能直接指导任务规划(Tasks)阶段？
□ 测试要求是否为红绿重构循环提供明确指导？
□ 任务序列是否支持增量构建和持续验证？
□ 整体规划是否形成从需求到TDD实施指导的完整链条？
```
**创作要求**：确保实施规划输出能无缝成为任务执行输入，体现贯通流程的严格依赖关系和TDD主场的核心价值。

### 🤖 AI协作执行指导

**基于实战提示词的具体执行约束**：

#### 📁 文件操作和格式约束
- **文件操作**: AI必须根据**输出目标与格式原则**创建对应的`implementation/`目录结构（实战模式优先）或等效载体。
- **格式严格要求**：必须格式化为最多两级层次结构的编号复选框列表
  - 顶层项目（如史诗）仅在需要时使用
  - 子任务使用十进制表示法编号（例如，1.1、1.2、2.1）
  - 每个项目都必须是一个复选框
  - 偏好简单结构，避免过度复杂的嵌套
- **任务信息完整性**：每个任务项必须包括：
  - 明确的编码目标作为任务描述
  - 作为任务下子弹点的附加信息
  - 对需求文档中需求的具体引用（引用细粒度的子需求）

#### 🎯 TDD转换专责执行
- **核心转换任务**：严格按照以下指令执行
  ```
  将功能设计转换为implementation/目录结构，为后续TDD代码生产阶段提供测试驱动的任务指导。
  优先考虑最佳实践、增量进度和早期测试，确保在任何阶段都不会出现大的复杂性跳跃。
  ```
- **增量构建强制**：确保每个提示都建立在先前提示的基础上
- **集成收尾**：以将所有内容连接在一起结束
- **悬空代码禁令**：不应有未集成到上一步中的悬空或孤立代码
- **测试驱动优先**：应在适当情况下优先考虑测试驱动开发

#### 🔒 代码导向严格约束
- **任务可操作性保证**：每个任务必须满足：
  - 涉及编写、修改或测试特定的代码组件
  - 指定需要创建或修改哪些文件或组件
  - 足够具体，编码代理无需额外澄清即可执行
  - 专注于实施细节而不是高级概念
  - 限定于特定的编码活动
- **明确排除非编码任务**：绝对不能包含：
  - 用户验收测试或用户反馈收集
  - 部署到生产或预演环境
  - 性能指标收集或分析
  - 用户培训或文档创建
  - 业务流程变更或组织变更
  - 营销或沟通活动
  - 任何无法通过编写、修改或测试代码完成的任务

#### 🔍 依赖验证和覆盖性检查
- **基础依赖**：任务文档必须基于设计文档，确保设计文档首先存在
- **需求覆盖**：必须确保所有需求都由实施任务覆盖
- **设计覆盖**：必须确保计划涵盖可通过代码实现的设计的所有方面
- **上下文假设**：必须假设在实施期间所有上下文文档（功能需求、设计）都将可用
- **早期验证**：应安排步骤以通过代码尽早验证核心功能

#### 💬 交互标准化协议
- **标准询问话术**：必须使用固定话术"任务看起来可以吗？"
- **批准标准明确**：只接受"是"、"已批准"、"看起来不错"等明确正面回应
- **修改请求处理**：如用户请求更改或未明确批准，必须对任务文档进行修改
- **循环终止条件**：继续反馈-修订循环，直到收到明确批准
- **工作流完成标志**：一旦任务文档获得批准，必须停止并清楚传达工作流已完成

#### 🔄 上溯和差距处理机制
- **需求差距**：如发现需求理解差距，必须提议返回需求步骤
- **设计差距**：如发现设计不完整，必须提议返回设计步骤
- **实施差距**：如在实施规划期间发现技术难点，必须在规划阶段解决
- **依赖检查**：如用户指示需要对设计进行更改，必须返回到设计步骤

#### 🔄 贯通流程导向的AI协作
**核心理念**：AI协作必须体现实施规划作为TDD主场的关键转折作用

```
AI协作如何服务贯通流程：
TDD转换策略 → 确保设计方案能转化为可执行的测试驱动任务
增量构建设计 → 为后续AI精确执行提供安全的推进路径
任务可操作化 → 保证编码代理能无缝理解和执行每个任务
测试计划完备 → 为红绿重构循环提供详细的验证指导
```

**AI执行要求**：严格遵循TDD转换的专业职责，确保实施规划的测试驱动特色和贯通流程主场地位

## 🚨 常见违反原则的行为

### ❌ TDD转换违反
- 任务中不包含测试驱动的执行方式
- 忽略测试优先的设计思维
- 任务序列不支持红绿重构循环

### ❌ 格式标准违反
- 任务描述过于抽象或高层
- 缺少需求文档的具体引用
- 任务层次结构过于复杂

### ❌ 代码导向违反
- 包含部署、培训等非编码任务
- 任务描述不够具体，难以执行
- 忽略任务的可操作性要求

### ❌ 增量构建违反
- 任务之间缺少逻辑依赖关系
- 复杂性跳跃过大
- 出现悬空的孤立任务

**修正策略**：发现违反后重新审视任务分解，确保符合TDD转换和增量构建要求

## 🎯 应用此原则

### 📝 内容创作者使用方法
1. **规划前准备**：深入理解设计文档，明确TDD转换目标
2. **规划中执行**：严格按照格式标准分解任务，确保增量构建
3. **规划后验证**：使用质量检查清单全面检查
4. **交付时把关**：严格执行质量门禁流程

### 🔧 TDD转换技巧
- **测试先行思维**：为每个功能先考虑如何测试
- **小步快跑**：将复杂功能分解为多个可测试的小任务
- **验证节点**：在关键节点设置集成测试和验证

### 📊 质量保证要求
- 定期review任务列表是否符合TDD转换要求
- 验证任务的可操作性和连贯性
- 确保测试计划的完备性

### 📊 质量标准维度
1. **贯通流程体现度**：是否清楚体现与前后阶段的严格依赖关系
2. **专业分工清晰度**：是否明确定义实施规划阶段应做和不应做的内容
3. **TDD定位准确度**：是否正确定位TDD在实施规划阶段的主场作用
4. **输入输出对接完整度**：是否确保与前后阶段的无缝衔接
5. **用户友好度**：是否避免专业术语，使用通俗易懂表达
