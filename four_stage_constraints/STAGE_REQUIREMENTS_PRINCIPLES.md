## 🔄 贯通流程中的需求定位

### 贯通流程理念在需求阶段的体现
**核心认知转变**：需求澄清不是独立技能，而是贯通流程中的专业分工

```
贯通流程中的需求(Requirements)澄清定位：
业务想法 → [需求(Requirements)澄清专业分工] → 结构化需求规格 → [设计(Design)阶段输入]
              ↑                      ↓
          专注用户故事           严格输出标准
          验收标准定义           质量门禁机制
              ↓                      ↓
      避免技术实现讨论         为设计(Design)阶段提供完整依据
```

### 严格依赖关系的价值
- **避免信息丢失**：业务需求完整转化为标准化规格文档
- **确保质量递进**：通过质量门禁确保需求质量再进入设计(Design)
- **支持AI精确理解**：结构化输出便于后续AI辅助设计(Design)和开发
- **建立系统思维**：从需求开始就考虑如何服务于最终测试计划

### 与后续阶段的输入输出对接
```
需求(Requirements)澄清阶段在贯通流程中的职责：
输入：业务想法、用户痛点、功能构想。
处理：结构化梳理、验收标准化、边界条件明确。
输出：**需求(Requirements)规格交付物** (`requirements/` 或等效载体)，该交付物将成为设计(Design)阶段的唯一输入依据。
质量门禁：明确批准机制，确保输出质量。
```

## 🎯 边界约束原则

### ❌ 严禁行为
- **不专注于代码探索**：需求阶段绝不涉及任何代码实现细节
- **不进行技术研究**：避免深入技术解决方案的讨论
- **不设计接口**：不涉及API设计、数据库设计等技术架构

### ✅ 专注职责
- **业务需求理解**：专注用户故事和业务价值
- **验收标准定义**：确保每个需求都有明确的可测试标准
- **边缘情况考虑**：识别异常情况和特殊场景

### 🧪 TDD在需求阶段的正确定位

**核心原则**：验收标准可测试性，但不涉及测试实施

```
TDD在需求阶段的职责边界：
✅ 应该做：验收标准的可测试性设计
✅ 应该做：使用"Given-When-Then"格式确保可验证性
✅ 应该做：考虑边缘情况的测试场景
❌ 不应做：编写具体测试用例
❌ 不应做：讨论测试框架和工具
❌ 不应做：进行测试实施规划
```

**价值体现**：为实施规划(Implementation)阶段（TDD真正主场）提供完整的测试需求基础

**创作要求**：任何需求(Requirements)阶段内容都必须严格遵循边界约束，将技术内容留给设计(Design)阶段，将测试实施留给实施规划(Implementation)阶段

## 📋 格式标准原则

### 🔥 基础格式要求（标准）
```markdown
功能需求文档标准格式：

概述部分：
[清晰的引言部分，总结该功能]

需求列表：
1. [需求类别]
   用户故事：作为[角色]，我想要[功能]，以便[好处]
   
   验收标准（Given-When-Then格式）：
   - Given [前置条件] When [操作] Then [预期结果]
   - Given [前置条件] When [操作] Then [预期结果]

2. [需求类别]
   [重复相同格式]

边缘情况和约束：
- [边缘情况1]
- [技术约束1]  
- [用户体验要求1]
```

### 🚀 进阶格式选项（可选，复杂项目推荐）

> 📍 **快速指引**：简单项目使用基础格式即可。复杂项目可参考 [🔧 进阶需求分析技巧](#🔧-进阶需求分析技巧可选) 获得完整BDD指导

**基础BDD格式示例**：
```markdown
Feature: [功能名称]
  作为 [角色]，我想要 [功能]，以便 [好处]

  Scenario: [场景名称]
    Given [前置条件]
    When [用户操作]
    Then [预期结果]
```

**适用判断**：企业级项目、多角色协作、复杂业务逻辑、长期维护项目

### 📊 Given-When-Then格式严格要求
- **Given-When-Then**：每个验收标准必须包含完整的三要素
- **可测试性**：每个标准都必须能够被验证
- **具体化**：避免模糊表达，使用具体的数值和条件

### 🔄 贯通流程导向的格式设计
**设计理念**：格式不仅是标准化工具，更是贯通流程的对接机制

```
格式如何服务贯通流程：
用户故事格式 → 为设计(Design)阶段提供业务理解基础
Given-When-Then验收标准 → 为实施规划(Implementation)提供测试设计输入
边缘情况清单 → 为设计(Design)阶段提供架构考虑要素
技术约束说明 → 为设计(Design)阶段提供限制条件
```

**创作要求**：所有需求文档必须严格遵循此格式，确保输出能无缝对接设计(Design)阶段输入

  Feature: [功能B]

```markdown
| 角色类型 | 核心需求 | 权限等级 | 业务场景 |

```

## 🔒 质量门禁原则

### 📋 审批流程要求
```
需求文档完成后的强制流程：
1. 创建requirements/目录结构，包含完整的需求文档体系
2. 填写完整的格式化内容到各个专项文档中
3. 必须询问："需求看起来可以吗？如果可以，我们可以继续进行设计。"
4. 等待明确批准（"是"、"已批准"、"看起来不错"等）
5. 如未获批准，必须修改后重新请求批准
6. 继续反馈-修订循环，直到获得明确批准
```

### 🔄 反馈-修订循环机制
- **无自动推进**：绝不能在未获得明确批准前进入设计阶段
- **持续修订**：必须根据用户反馈持续完善需求文档
- **批准标准**：只有收到明确的正面回应才能继续

### 🎯 质量检查标准（机器可执行清单）

#### 📝 内容完整性检查
- [ ] **用户故事格式检查**：每个需求都包含“作为[Role]，我想要[Function]，以便[Benefit]”完整三要素
- [ ] **Given-When-Then格式检查**：每个验收标准包含Given（前置条件）-When（操作）-Then（预期结果）
- [ ] **边缘情况枚举检查**：列出至少3个异常/特殊场景，为设计(Design)阶段提供考虑要素

#### ⛔ 边界约束检查
- [ ] **技术实现禁止检查**：文档中不包含任何代码语言、框架、数据库技术描述
- [ ] **API/架构禁止检查**：文档中不包含API设计、数据库设计、系统架构描述
- [ ] **TDD实施禁止检查**：文档中不包含测试代码、测试框架选择、TDD执行计划

#### 🔗 贯通流程对接检查
- [ ] **输出格式检查**：生成requirements/目录结构（实战模式）或requirements.md（教学模式），符合设计(Design)阶段输入要求
- [ ] **批准流程检查**：使用标准话术“需求看起来可以吗？如果可以，我们可以继续进行设计。”
- [ ] **明确批准获得**：收到用户的“是”、“已批准”、“看起来不错”等明确正面回应

### 🔄 贯通流程质量递进机制
**核心价值**：质量门禁不仅保证当前阶段质量，更确保贯通流程的流畅性

```
质量门禁在贯通流程中的作用：
当前阶段质量保证 → 避免质量问题向后传递
输出标准化验证 → 确保下阶段输入的可用性
依赖关系确认 → 验证前后阶段的对接完整性
系统思维培养 → 强化"前阶段输出=后阶段输入"意识
```

**创作要求**：质量门禁是不可跳过的强制环节，确保需求质量和贯通流程连续性

### 🤖 AI协作执行指导

**基于实战提示词的具体执行约束**：

#### 📁 文件操作约束
- **文件操作**: AI必须根据**输出目标与格式原则**创建对应的`requirements/`目录结构（实战模式优先）或等效载体。
- **初始版本生成**：基于用户粗略想法生成需求文档初始版本，无需先按顺序提问
- **完整性保证**：确保文档包含引言、需求列表、边缘情况等所有必需部分
- **版本管理**：每次修改后保存完整版本，确保可追溯性

#### 🎯 执行节奏精确控制
- **一次性生成原则**：首次根据功能构想生成完整初始需求，避免碎片化询问
- **集中修改策略**：基于用户反馈进行集中修改，而非逐项确认
- **边缘考虑强制**：必须主动考虑边缘情况、用户体验、技术约束和成功标准
- **建议提供机制**：可建议需要澄清或扩展的具体领域，为用户提供选项
- **🚀 格式智能推荐**：根据项目特征推荐基础格式或BDD格式（详见[进阶技巧](#🔧-进阶需求分析技巧可选)）

#### 💬 交互标准化协议
- **标准询问话术**：必须使用固定话术"需求看起来可以吗？如果可以，我们可以继续进行设计。"
- **批准标准明确**：只接受"是"、"已批准"、"看起来不错"等明确正面回应
- **修改请求处理**：如用户请求更改或未明确批准，必须对需求文档进行修改
- **循环终止条件**：继续反馈-修订循环，直到收到明确批准

#### 🚫 严格禁令强化
- **代码探索绝对禁令**：在此阶段绝对不专注于代码探索或技术实现细节
- **技术设计禁令**：不涉及任何架构设计、API接口设计、数据库设计
- **工具选择禁令**：不讨论开发工具、测试框架、技术栈选择
- **实现方式禁令**：不探讨具体的编程语言、框架或实现方式

#### 🔄 贯通流程导向的AI协作
**核心理念**：AI协作必须体现贯通流程的严格依赖关系

```
AI协作如何服务贯通流程：
需求生成策略 → 确保输出能无缝成为设计(Design)阶段输入
质量门禁执行 → 保证严格的前后阶段依赖关系
用户反馈处理 → 体现用户在贯通流程中的主导地位
禁令边界维护 → 确保专业分工原则不被违反
```

**AI执行要求**：严格遵循贯通流程导向的协作原则，确保需求阶段的专业分工边界和输出质量

## 📤 输出目标与格式原则

本阶段的输出必须能无缝成为下一阶段的输入。根据学习阶段的不同，采用对应的交付物格式。

#### 📤 输出目标与格式
- **交付物**: `requirements/` 或等效载体
- **结构示例** (泛化模式):
    ```
    requirements/
    ├── README.md                  # 需求文档结构总览和阅读指南
    ├── [项目背景文档]             # 示例: overview.md, business_case.md, project_context.md
    ├── [用户场景文档]             # 示例: user_stories.md, personas.md, use_cases.md  
    ├── [功能需求文档]             # 示例: functional_spec.md, features.md, capabilities.md
    ├── [约束条件文档]             # 示例: constraints.md, non_functional.md, limitations.md
    └── [其他专项文档]             # 根据项目类型: api_requirements.md, data_requirements.md等
    ```
    
    **智能选择矩阵**:
    ```
    项目类型        业务领域        文档组织策略              选择示例
    ───────────────────────────────────────────────────────────────────────
    Web应用         电商/企业       用户体验优先 + 业务流程      user_journeys.md, business_flows.md
    移动应用        社交/生活       场景化需求 + 用户活动      scenarios.md, user_activities.md
    AI/ML系统      数据/智能       数据需求 + 模型指标        data_requirements.md, model_specs.md
    区块链项目      金融/游戏       经济模型 + 安全需求        tokenomics.md, security_requirements.md
    IoT设备         工业/智能家居   硬件约束 + 连接協议        hardware_constraints.md, connectivity_specs.md
    企业系统        金融/医疗       合规要求 + 安全标准        compliance_requirements.md, security_standards.md
    ```
    
    **决策树指导**:
    1. **首先识别项目类型** → 确定技术架构特点
    2. **分析业务领域** → 识别特殊需求(合规、安全、性能)
    3. **评估团队规模** → 选择文档精度(简洁 vs 详细)
    4. **确定交付方式** → 选择组织结构(迭代 vs 瀑布)
- **AI智能适配算法**: 
  ```
  IF 项目类型 = "企业系统" THEN
      优先级 = [合规文档, 安全文档, 审计文档]
      命名风格 = "规范化编号式"
      细分程度 = "详细模式"
      
  ELIF 项目类型 = "AI/ML" AND 数据敏感度 = "高" THEN
      优先级 = [数据治理, 隐私保护, 模型可解释性]
      命名风格 = "功能语义式"
      细分程度 = "中等模式"
      
  ELIF 团队规模 <= 5 AND 交付周期 <= "2周" THEN
      优先级 = [核心功能, 用户体验]
      命名风格 = "简洁语义式"
      细分程度 = "精简模式"
  ```
  
  **反面指导** (避免错误):
  - ✘️ 勿在金融项目中使用非正式命名(feature_ideas.md)
  - ✘️ 勿在小团队项目中过度细分文档结构
  - ✘️ 勿在AI项目中忽略数据治理和伦理考量
  - ✓️ 始终确保输出能成为设计阶段的完整输入

### 🔗 严格依赖关系维护
**贯通流程核心机制**: 需求交付物将作为下一阶段（设计阶段）的严格输入。
```
依赖关系检查清单：
□ 需求交付物是否能无缝对接设计阶段的输入要求？
□ 验收标准是否为测试策略设计提供充分信息？
□ 边缘情况是否覆盖架构设计所需考虑因素？
□ 技术约束是否为设计方案选择提供边界条件？
□ 整体需求是否形成完整的业务逻辑闭环？
```
**创作要求**：确保需求阶段输出能无缝成为设计阶段输入，体现贯通流程的严格依赖关系。

## 🚨 常见违反原则的行为

### ❌ 贯通流程理解偏差
- **独立技能思维**：把需求澄清当作孤立环节，不考虑与设计阶段的输入输出对接
- **跳跃式推进**：不等质量门禁确认就推进到设计讨论
- **信息断裂**：需求输出格式不匹配设计阶段输入要求

### ❌ 边界违反
- 在需求中讨论"用Redis缓存"等技术实现
- 设计数据库表结构
- 讨论API接口格式
- **TDD越界**：在需求阶段编写具体测试用例或讨论测试框架

### ❌ 格式违反  
- 用户故事缺少"以便"部分
- 验收标准不使用Given-When-Then格式
- 使用模糊语言如"系统应该好用"
- **对接格式错误**：输出格式不符合设计阶段输入标准

### ❌ 门禁违反
- 未等待用户批准就开始设计讨论
- 收到否定反馈后不修改需求文档
- 使用模糊的询问方式而非标准话术
- **质量递进中断**：质量问题向后传递到设计阶段

**修正策略**：发现违反后立即回到需求澄清，重新执行正确的贯通流程，确保严格依赖关系

### 📝 内容创作者使用方法

3. **创作后验证**：使用质量检查清单自检
4. **交付时执行**：严格执行质量门禁流程

### 🔧 贯通流程质量保证要求

- **对接质量检查**：验证输出是否能无缝成为设计阶段输入
- **依赖关系检查**：确保严格的前后阶段依赖关系维护
- **持续改进机制**：定期review现有内容是否符合贯通流程原则要求
- **系统性反馈**：收集用户反馈，持续优化贯通流程应用效果

### 📊 质量标准维度
1. **贯通流程体现度**：是否清楚体现与设计阶段的严格依赖关系

3. **TDD定位准确度**：是否正确定位TDD在需求阶段的作用边界
4. **输入输出对接完整度**：是否确保与前后阶段的无缝衔接
5. **用户友好度**：是否避免专业术语，使用通俗易懂表达
