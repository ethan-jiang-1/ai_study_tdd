## 🔄 贯通流程中的任务规划定位

### 贯通流程理念在任务规划阶段的体现
**核心认知转变**：任务规划不是独立的编码工作，而是贯通流程的最终任务规划环节

```
贯通流程中的任务规划(Tasks)定位：
实施规划(Implementation)测试计划 → [任务规划(Tasks)专业分工] → TDD执行任务规划 → [TDD代码生产指导]
                ↑                         ↓
            TDD执行指导               执行任务规划清单
            上下文数据               质量验证方法
                ↓                         ↓
        贯通流程的文档闭环：从需求(Requirements)到TDD执行任务规划的完整链条
        TDD代码生产准备：基于完备测试计划的任务规划指导
```

### 严格依赖关系的价值
- **多阶段累积输入**：整合需求(Requirements)、设计(Design)、实施规划(Implementation)三阶段的所有成果
- **确保质量闭环**：通过回溯验证确保文档闭环符合原始需求(Requirements)
- **支持TDD代码生产**：基于完备上下文和测试计划为后续TDD代码生产提供指导
- **完成贯通闭环**：实现"需求(Requirements)→设计(Design)→实施规划(Implementation)→任务规划(Tasks)"的完整流程闭环

### 与前阶段的输入依赖关系
```
任务规划(Tasks)阶段在贯通流程中的职责：
输入：
- **需求(Requirements)规格交付物** (`requirements/` 或等效载体)
- **设计(Design)规格交付物** (`design/` 或等效载体)
- **实施规划(Implementation)规格交付物** (`implementation/` 或等效载体)
处理：TDD执行任务规划、验证方法制定、实施准备文档化。
输出：**任务规划(Tasks)规格交付物** (`tasks/` 或等效载体)，为后续TDD代码生产提供完整指导。
质量闭环：基于需求(Requirements)的多层次验证，完成贯通流程的最终文档闭环。
```

### 🧪 TDD在任务规划阶段的正确定位
**核心原则**：⭐ TDD的任务规划阶段 - 红绿重构循环的执行规划准备

```
TDD在任务规划阶段的核心职责：
✅ 应该做：规划TDD执行任务和验证方法
✅ 应该做：制定每个任务的执行步骤和验证标准
✅ 应该做：为后续TDD代码生产提供完整的任务清单
✅ 应该做：基于需求(Requirements)、设计(Design)、实施规划(Implementation)的多层次验证规划
❌ 不应做：修改测试计划（属于实施规划(Implementation)阶段职责）
❌ 不应做：直接进行代码生产（应通过`tasks/` 或等效载体进行指导后续TDD执行后输出代码）
```

**价值体现**：完成贯通流程的文档闭环：基于完备测试计划的TDD执行任务规划

## ⏰ 执行节奏控制原则

### 🎯 一次一个任务的严格要求
**核心约束**：一次只专注于一个任务，不要为其他任务进行文档化

### 📋 执行节奏具体规范
```
严格的执行流程：
1. 从任务列表中选择当前要执行的任务
2. 如果任务有子任务，必须从子任务开始
3. 专注执行当前任务，不涉及其他任务的功能
4. 完成当前任务后，立即停下来让用户查看
5. 绝不自动继续列表中的下一个任务
6. 等待用户确认或指定下一个任务
```

### 🔒 停止检查机制
- **任务完成标志**：当前任务的所有要求都已满足
- **强制停止**：完成后必须停下来，不能继续
- **用户确认**：等待用户查看和确认结果
- **下一步指示**：等待用户明确指定下一个任务

### 🚨 禁止行为
- **任务跳跃**：不能跳过当前任务去做其他任务
- **功能越界**：不能为其他任务实现功能
- **自动推进**：不能在用户未要求的情况下自动继续下一任务
- **批量执行**：不能一次性执行多个任务

### 🔄 贯通流程导向的节奏控制价值
**设计理念**：节奏控制不仅保证执行质量，更体现贯通流程的精确实施理念

```
节奏控制如何服务贯通流程：
一次一任务精确执行 → 确保每个任务都符合最初需求
用户控制节奏 → 保证贯通流程的可视化和可控性
任务间验证 → 确保每个環节都符合质量标准
增量交付保证 → 在任何时点停止都有可交付成果
```

**创作要求**：任务规划必须严格遵循节奏控制，体现贯通流程的精确性和用户的主导权

## 📚 上下文完整性原则

### 📋 执行前强制检查
**在执行任何任务之前，必须确保已阅读所有上游交付物**：
- **需求(Requirements)规格交付物**：理解原始的业务需求。
- **设计(Design)规格交付物**：理解技术架构和方案。
- **实施规划(Implementation)规格交付物**：理解任务分解和测试计划。

### ❌ 无上下文执行的危险
```
没有需求或设计就执行任务 → 导致不准确的实现
缺少任务详细信息 → 导致实现偏离预期
忽略验收标准 → 导致质量不符合要求
```

### ✅ 上下文完整性检查清单
- [ ] 已完整阅读需求(Requirements)规格交付物，理解功能需求
- [ ] 已完整阅读设计(Design)规格交付物，理解技术架构
- [ ] 已完整阅读实施规划(Implementation)规格交付物，理解任务分解
- [ ] 理解当前任务在整体项目中的位置
- [ ] 明确当前任务的输入和输出要求

### 🔗 上下文应用要求
- **需求对照**：实现过程中持续对照需求(Requirements)文档
- **设计遵循**：严格按照设计(Design)文档的架构实现
- **任务细节**：严格按照任务描述的具体要求
- **版本一致**：确保使用最新版本的上下文文档

### 🔄 贯通流程导向的上下文完整性价值
**设计理念**：上下文完整性是贯通流程最终成功的关键保证

```
上下文完整性如何服务贯通流程：
需求(Requirements)文档依赖 → 确保实现符合原始业务意图
设计(Design)文档依赖 → 确保技术实现符合架构设计
实施规划(Implementation)文档依赖 → 确保执行顺序和测试计划的严格遵循
三阶段累积依赖 → 实现贯通流程的知识传递和价值累积
```

**创作要求**：绝不允许在上下文不完整的情况下执行任务，确保贯通流程知识传递的完整性和准确性

## ✅ 验证机制原则

### 🎯 基于需求(Requirements)的验证要求
**根据任务或其详细信息中指定的任何需求(Requirements)验证实现**

### 📋 验证层次结构
```
多层次验证机制：
1. 任务级验证：当前任务的具体要求是否满足
2. 需求(Requirements)级验证：相关的需求条目是否得到正确实现
3. 设计(Design)级验证：实现是否符合设计文档的架构
4. 集成级验证：与已有功能的集成是否正常
```

### 🧪 验证方法要求
- **功能验证**：验证功能是否按预期工作
- **边界验证**：验证边缘情况的处理
- **性能验证**：验证是否满足性能要求
- **安全验证**：验证安全相关的实现

### 📊 验证标准检查
- [ ] 实现满足任务描述的所有要求
- [ ] 实现符合引用的需求(Requirements)条目
- [ ] 实现遵循设计(Design)文档的约束
- [ ] 实现通过了相应的测试用例
- [ ] 实现处理了已知的边缘情况

### 🔄 贯通流程导向的验证机制价值
**设计理念**：验证机制是贯通流程质量闭环的关键环节

```
验证机制如何服务贯通流程：
任务级验证 → 确保当前任务的技术实现质量
需求(Requirements)级验证 → 确保回溯到原始业务需求的符合性
设计(Design)级验证 → 确保技术架构和设计决策的一致性
集成级验证 → 确保整个贯通流程成果的系统一致性
```

**验证层次升级**：从单点验证升级到多层次回溯验证
```
基础验证：任务需求(Requirements) → 任务规划(Tasks) → 验证计划
贯通验证：原始需求(Requirements) → 设计(Design)方案 → 实施规划(Implementation)计划 → 任务规划(Tasks) → TDD指导完整性
```

**创作要求**：每个任务完成后必须进行多层次验证，确保贯通流程的质量闭环完整性

## 🔍 任务问题处理原则

### 🎯 区分执行请求和信息查询
**重要区别**：用户可能询问有关任务的问题，而不想执行它们

### 📋 问题类型识别
```
信息查询类（不执行任务）：
- "下一个任务是什么？"
- "这个功能有哪些任务？"
- "任务X的详细要求是什么？"

执行请求类（需要执行任务）：
- "执行任务1.1"
- "开始实现用户登录功能"
- "继续下一个任务"
```

### 💡 正确响应策略
- **信息查询**：只提供信息，不启动任何任务执行
- **执行请求**：按照执行节奏控制原则执行任务
- **模糊请求**：主动询问用户的具体意图

### 🚨 错误处理
- **任务未指定**：查看任务列表并就下一个要执行的任务提出建议
- **任务不存在**：提醒用户任务不存在，提供可选任务列表
- **依赖未满足**：提醒用户完成前置任务

### 🔄 贯通流程导向的问题处理价值
**设计理念**：问题处理机制保证贯通流程的准确执行和用户主导

```
问题处理如何服务贯通流程：
意图识别精确性 → 避免贯通流程的错误执行和偏离
执行请求响应 → 确保贯通流程按照用户意图推进
信息查询支持 → 为用户提供贯通流程的透明可视
问题解决指导 → 帮助用户解决贯通流程中的障碍
```

**创作要求**：准确识别用户意图，保证贯通流程的准确执行和用户主导权，避免流程偏离和错误执行

## 📤 输出目标与格式原则

本阶段的输出是贯通流程的最终交付物，为后续的TDD代码生产提供完整指导。

#### 📤 输出目标与格式
- **交付物**: `tasks/` 或等效载体
- **结构示例** (泛化模式):
    ```
    tasks/
    ├── README.md                  # TDD执行任务规划总览
    ├── [核心逻辑任务]               # 示例: core_tasks.md, business_logic.md, domain_tasks.md
    ├── [用户界面任务]               # 示例: ui_tasks.md, frontend_tasks.md, client_tasks.md
    ├── [数据层任务]                 # 示例: data_tasks.md, persistence_tasks.md, storage_tasks.md
    ├── [集成测试任务]               # 示例: integration_tasks.md, e2e_tasks.md, system_tasks.md
    └── [专项技术任务]               # 根据项目类型: ml_tasks.md, blockchain_tasks.md等
    ```
    
    **执行优先级矩阵**:
    ```
    团队模式        交付压力        任务执行策略              优先级排序原则
    ───────────────────────────────────────────────────────────────────────────────────────────────────
    敏捷小组        高速迭代        功能切片 + 快速验证         MVP功能 → 核心流程 → 优化特性
    企业团队        稳定交付        模块化 + 并行开发         基础设施 → 业务模块 → 集成测试
    分布式团队      异步协作        服务边界 + 独立部署         契约定义 → 服务实现 → 端到端测试
    开源社区        贡献驱动        文档完善 + 新手友好         文档 → 示例 → 核心功能 → 高级特性
    研发团队        创新驱动        实验驱动 + 快速失败         假设验证 → 核心算法 → 工程化
    ```
    
    **交付节奏控制**:
    1. **微交付模式** → 每个任务都能独立验证和部署
    2. **可视化进展** → 每日都有可演示的成果增量
    3. **风险控制** → 高风险任务优先实现和验证
    4. **质量门禁** → 每个交付点都有自动化质量检查
- **AI执行协调引擎**:
  ```
  // 团队协作模式识别
  IF team.distribution == "remote" AND team.timezone_span > 8 THEN
      execution_style = "asynchronous_handoff"
      documentation_detail = "comprehensive"  // 需要详细文档支持异步协作
      verification_points = "milestone_based"  // 重要里程碑验证
      
  // 交付紧急度评估  
  ELIF project.deadline <= "2_weeks" AND quality.requirements == "production" THEN
      execution_style = "parallel_streams"
      verification_points = "continuous"  // 持续集成和测试
      task_granularity = "4_hours_max"  // 小粒度快速反馈
      
  // 新手团队支持
  ELIF team.experience == "junior" OR tech_stack.familiarity == "low" THEN
      execution_style = "guided_sequential"
      documentation_detail = "tutorial_style"  // 教学式文档
      verification_points = "per_task_review"  // 每任务都要review
  ```
  
  **执行质量保障**:
  - ✘️ 勿在距离协作中省略沟通成本和上下文传递
  - ✘️ 勿在紧急项目中过度压缩测试和文档环节
  - ✘️ 勿在新手团队中过度并行化任务执行
  - ✓️ 始终保持任务的原子性和可回滚性

### 🔗 严格依赖关系维护
**贯通流程核心机制**: 任务规划阶段的输出是整个贯通流程的最终文档化成果。
```
依赖关系检查清单：
□ 执行输入是否整合了前三阶段的所有成果？
□ TDD执行任务规划是否完整涵盖红绿重构的指导方法？
□ 任务规划是否能追溯到原始需求和设计决策？
□ 最终交付物（文件或目录）是否形成了完整的贯通流程文档闭环？
```
**创作要求**：确保任务规划阶段完成TDD执行任务规划文档，为后续TDD代码生产提供完整指导。

### 🤖 AI协作执行指导

**基于实战提示词的具体执行约束**：

#### 📚 上下文完整性强制验证
- **三文档必读**：在执行任何任务之前，务必确保已阅读：
  - requirements/规格交付物（功能需求文档体系）
  - design/规格交付物（设计文档体系）
  - implementation/规格交付物（任务分解文档体系）
- **危险警告**：在没有需求(Requirements)或设计(Design)的情况下执行任务将导致不准确的实现
- **上下文应用**：理解当前任务在整体项目中的位置和依赖关系
- **版本一致性**：确保使用最新版本的所有上下文文档

#### 🎯 一次一任务严格控制
- **单任务专注**：一次只专注于一个任务，不要为其他任务实现功能
- **子任务优先原则**：如果请求的任务有子任务，请始终从子任务开始
- **完成即停止**：完成请求的任务后，请停下来让用户查看
- **禁止自动推进**：不要直接继续列表中的下一个任务
- **核心原则强调**：记住，一次只执行一个任务非常重要，完成一个任务后就停下来

#### 🔍 需求(Requirements)验证和实现检查
- **验证要求**：根据任务或其详细信息中指定的任何需求(Requirements)验证实现
- **追溯检查**：确保实现满足引用的需求(Requirements)条目
- **质量标准**：实现必须符合设计(Design)文档的架构约束
- **边缘情况处理**：考虑并处理已知的边缘情况

#### 💡 任务建议和问题处理机制
- **任务未指定处理**：如果用户没有指定想处理哪个任务，查看任务列表并就下一个要执行的任务提出建议
- **意图识别关键**：用户可能询问有关任务的问题，而不想执行它们，在这种情况下，不要总是开始执行任务
- **信息查询示例**：
  - "下一个任务是什么？" → 只提供信息，不启动任务
  - "这个功能有哪些任务？" → 只提供信息，不启动任务
  - "任务X的详细要求是什么？" → 只提供信息，不启动任务
- **执行请求识别**：明确的执行指令才启动任务执行

#### 🚫 自动化行为严格禁令
- **禁止批量执行**：绝对不要在没有用户要求的情况下自动继续下一个任务
- **禁止任务跳跃**：不能跳过当前任务去做其他任务
- **禁止功能越界**：不能为其他任务实现功能
- **禁止假设推进**：不能假设用户想要继续执行更多任务

#### 🔄 贯通流程导向的AI协作
**核心理念**：AI协作必须体现任务规划作为贯通流程最终环节的精确实施价值

```
AI协作如何服务贯通流程：
上下文完整性验证 → 确保AI基于全流程知识进行精确的文档化工作
一次一任务控制 → 保证贯通流程的可控推进和质量验证
需求验证机制 → 实现从原始需求到TDD执行任务规划的完整追溯
用户主导权维护 → 确保用户在贯通流程中的控制和决策权
```

**AI执行关键原则**：
1. **上下文优先**：没有完整上下文绝不开始执行
2. **单任务专注**：一次只做一件事，做完就停
3. **用户控制**：让用户决定节奏和方向
4. **质量验证**：每个任务都要验证需求符合性

**AI执行要求**：严格遵循贯通流程的文档化原则，确保任务规划阶段的AI协作精确性和用户主导权

## 🚨 常见违反原则的行为

### ❌ 贯通流程理解偏差
- **独立规划思维**：把任务规划当作孤立的编码工作，不考虑与前三阶段的对接
- **执行闭环中断**：没有实现"需求(Requirements)→设计(Design)→实施规划(Implementation)→任务规划(Tasks)"的完整闭环
- **规划完整性缺失**：未能基于完备测试计划完成TDD执行任务规划

### ❌ 执行节奏违反
- 一次性执行多个任务而不停止
- 完成任务后自动继续下一个任务
- 为其他任务实现功能
- **节奏控制破坏**：破坏贯通流程的精确性和可控性

### ❌ 上下文完整性违反
- 没有阅读需求(Requirements)文档就开始实现
- 忽略设计(Design)文档的架构约束
- 不理解任务在整体项目中的位置
- **知识传递中断**：破坏贯通流程的知识累积和传递

### ❌ 验证机制违反
- 不根据需求(Requirements)验证实现
- 跳过测试用例的验证
- 忽略边缘情况的处理
- **质量闭环破坏**：破坏贯通流程的质量保证机制

### ❌ 问题处理违反
- 对信息查询也启动任务执行
- 对执行请求只提供信息不执行
- 不明确用户意图就贸然行动
- **用户主导权破坏**：影响用户对贯通流程的主导和控制

**修正策略**：发现违反后立即停止，重新按照正确的贯通流程执行，确保严格依赖关系和最终质量

## 🎯 应用此原则

### 📝 内容创作者使用方法
1. **执行前准备**：确保上下文文档完整，理解任务要求

3. **执行后验证**：全面验证实现质量和需求符合性

- **验证自动化**：设计基于贯通流程的自动化验证机制
- **闭环保证**：确保AI执行能实现贯通流程的完整闭环

- **规划完整性检查**：持续优化TDD执行任务规划的支撑机制和完整性
