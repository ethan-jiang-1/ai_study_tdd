## 演示1：开场冲击 - AI代码的隐患分析

### 用途：建立问题意识，引发认知冲突

### 演示脚本

**展示场景**：用户登录功能的AI生成代码
```javascript
// "完美"的AI生成代码
function login(email, password) {
    if (email && password) {
        const user = database.find(u => u.email === email);
        if (user && user.password === password) {
            return { success: true, user: user };
        }
    }
    return { success: false, message: "登录失败" };
}
```

**分析引导过程**：
1. **初印象收集**："这段代码看起来怎么样？"
2. **系统性分析**："我们从安全、功能、可维护性三个角度分析"
3. **问题归类整理**：
   - 安全问题：密码明文比较、无防暴力破解
   - 功能问题：错误信息不明确、异常处理缺失
   - 设计问题：紧耦合、难以测试

**核心洞察揭示**：
> "AI擅长模式识别，但缺乏边界思考。这就是为什么我们需要测试来约束和指导AI。"

## 演示4：风险洞察驱动的测试设计

### 用途：对比覆盖率思维vs风险思维

### 演示场景：支付系统测试策略

**传统覆盖率方法展示**：
```javascript
// 传统测试：追求覆盖率
describe('支付服务', () => {
  test('正常支付流程', () => {
    // 基础功能测试，覆盖主要代码路径
  });
  
  test('参数验证', () => {
    // 边界值测试，提升覆盖率
  });
  
  // ... 更多测试用例，目标80%覆盖率
});
```
**结果**：覆盖率80%，但仍有关键风险遗漏

**AI风险驱动方法展示**：

*步骤1：工具分析*
```bash
# CodeScene分析结果
高风险模块：PaymentProcessor.processPayment()
- 圈复杂度: 15 (建议<10)  
- 修改频率: 每月8次
- 业务影响: 极高(涉及资金)
```

*步骤2：AI深度分析*
```
输入给Claude：
"基于这个风险分析，作为支付系统专家，请识别processPayment方法的核心风险点，并设计相应测试。"

Claude输出：
"识别出3个核心风险：
1. 并发风险：多个支付请求的竞态条件
2. 一致性风险：支付状态与订单状态不同步  
3. 恢复风险：异常情况下的数据恢复"
```

*步骤3：针对性测试生成*
```javascript
// AI生成的风险驱动测试
describe('支付系统核心风险测试', () => {
  test('并发支付竞态条件防护', async () => {
    // 模拟100个并发支付请求
    const promises = Array(100).fill().map(() => 
      paymentService.processPayment(orderId, amount)
    );
    
    const results = await Promise.all(promises);
    const successCount = results.filter(r => r.success).length;
    
    // 断言：只能有一个成功支付
    expect(successCount).toBe(1);
  });
  
  test('支付异常时的数据一致性', async () => {
    // 模拟第三方支付异常
    mockThirdPartyAPI.mockRejectedValue(new Error('网络超时'));
    
    await expect(
      paymentService.processPayment(orderId, amount)
    ).rejects.toThrow();
    
    // 验证：订单状态应该回滚，资金不应扣除
    const order = await orderService.getOrder(orderId);
    expect(order.status).toBe('PENDING');
    expect(await getUserBalance(userId)).toBe(originalBalance);
  });
});
```

**效果对比表**：
| 方法 | 测试用例数 | 代码覆盖率 | 关键风险覆盖 | 发现Bug率 |
|------|------------|------------|--------------|-----------|
| 传统覆盖率 | 25个 | 85% | 40% | 60% |
| AI风险驱动 | 12个 | 65% | 95% | 90% |

## 互动环节设计

### 互动1：问题分析训练（15分钟开场后）

**目标**：训练系统性分析思维

**流程**：
1. **展示代码**（2分钟）：用户注册功能的AI代码
2. **小组讨论**（5分钟）：3-4人一组，分析问题
3. **分类汇报**（6分钟）：按安全、功能、设计三类汇报
4. **总结提升**（2分钟）：讲师补充遗漏点

**引导技巧**：
- "请从架构师的角度思考"
- "如果这代码上线了会怎样？"
- "还有其他角度的问题吗？"

### 互动2：认知模式转换（45分钟时）

**目标**：让学员体验认知负荷的重新分配

**活动设计**：
```
场景：实现一个复杂的订单处理逻辑

传统方式：
- 学员A：手写全部代码（15分钟）
- 结果：累，容易出错

AI协作方式：  
- 学员B：先设计测试场景，AI生成实现（15分钟）
- 结果：轻松，质量更高
```

**体验对比**：
- 心理感受：累 vs 轻松
- 思考重点：语法细节 vs 业务逻辑
- 产出质量：基本功能 vs 完整方案

### 互动3：路径评估与选择（90分钟时）

**目标**：个性化学习路径推荐

**评估问卷**：
```
1. 你的TDD/BDD经验水平？
   □ 完全新手  □ 有所了解  □ 经常使用

2. 你更偏向哪种学习方式？
   □ 理论先行  □ 实践先行  □ 理论实践并重

3. 你的学习时间安排？
   □ 集中学习  □ 碎片学习  □ 弹性安排

4. 你对AI工具的熟悉度？
   □ 很少使用  □ 基础使用  □ 深度使用
```

**个性化建议**：
- **理论型学习者** → 系统深化路径
- **实践型学习者** → 快速体验路径  
- **平衡型学习者** → 混合进阶路径

### 互动4：方法论内化（结束前10分钟）

**目标**：确保核心概念被理解和内化

**三个关键问题**：
1. "AI+TDD的核心价值用一句话概括？"
2. "测试在AI协作中扮演什么角色？"  
3. "你明天就可以开始的第一步是什么？"

**期望答案要点**：
1. 让AI更好地理解和实现人类意图
2. 测试是人机协作的"合同"和"接口"
3. 选择工具，找个小功能试试测试先行

## 教学节奏控制

### 时间分配策略

**第一部分：开场冲击（15分钟）**
- 核心：建立问题意识
- 节奏：快速展示，深度分析
- 重点：让学员看到AI的局限性

**第二部分：核心洞察（30分钟）**
- 核心：认知模式转换
- 节奏：理论+案例+体验
- 重点：理解人机协作的本质

**第三部分：解决方案（45分钟）**
- 核心：系统方法论
- 节奏：循序渐进，逐步深入
- 重点：建立完整的知识框架

**第四部分：实践路径（25分钟）**
- 核心：个性化指导
- 节奏：评估+推荐+计划
- 重点：明确下一步行动

**第五部分：立即行动（5分钟）**
- 核心：降低开始门槛
- 节奏：简单明确
- 重点：今天就能开始做的事

### 弹性内容设计

**如果时间不够**：
- 压缩第三部分的8个维度到4个维度
- 简化互动环节，保留核心讨论
- 重点保证开场冲击和路径指导

**如果时间充足**：
- 增加现场编程演示
- 深入讨论复杂场景
- 更多的互动和Q&A

### 技术准备
- **环境配置**：Claude账号、代码编辑器、演示项目
- **案例准备**：预先测试所有演示代码

- **深度理解**：八大维度的理论基础
- **案例储备**：不同行业的具体应用案例
- **问答预案**：常见问题的标准回答

### 心理准备
- **受众心理**：理性分析型学员的特点
- **节奏把控**：逻辑推进的时间感知
- **应变能力**：面对质疑和挑战的应对

这套演示方案专门为问题驱动式教学框架设计，强调逻辑分析、系统思考和渐进深入，适合偏理性思维的受众群体。
